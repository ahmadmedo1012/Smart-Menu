# خطة الإتقان الشاملة — Smart Menu (menu.smart-link.ly)
**مبنية على فحص فعلي لمستودع `ahmadmedo1012/Smart-Menu`** — آخر كوميت: `75e5ce7f` بتاريخ 2 سبتمبر 2026.
هذه الخطة ليست تخمينًا؛ كل بند فيها إما (أ) مؤكَّد بالفحص المباشر للكود، أو (ب) مصنَّف صراحة كـ"يحتاج تحقق" لأنه لم يُثبت بالفحص.

---

## 0) الوضع الحالي فعليًا (لا تعد اختراع العجلة)

المشروع مرّ فعلًا بـ **78+ جولة إصلاح وتدقيق موثقة** في `docs/round*.md`، وفيه:
- تدقيق أمني شامل (rate limiting, CSRF, تشفير الأسرار، HMAC/AES-GCM) — منفَّذ ومؤكَّد.
- تدقيق إمكانية وصول (a11y / axe-core) — منفَّذ.
- 34 صفحة، 64 مسار API، 127 مكوّن React، نظام ألوان بـ oklch tokens في `globals.css` (1058 سطر، 140 استخدام oklch).
- `CLAUDE.md` يفرض بالفعل استخدام 7 أدوات/مهارات إلزامية (gstack, impeccable, ast-grep-mcp, axe-core, Understand-Anything, ui-ux-pro-max, claude-mem) + تنسيق عبر Ruflo swarm.

**لذلك:** هذه الخطة لا "تعيد الإصلاح من الصفر" — بل تُغلق الفجوات المتبقية المؤكَّدة، وتُحوّل الالتزام بالأدوات من "بند في ملف تعليمات" إلى **بوابة تحقق إلزامية بعد كل مرحلة**، لأن وكيل الذكاء لا يُفترض أن يُصدَّق بمجرد قوله "التزمت بالقواعد" — بل بإثبات تنفيذي.

## 2) المبدأ الحاكم: لا تنفيذ منفرد من الوكيل — كل مرحلة أدوات + إثبات

هذا هو تحديدًا ما طلبته: الوكيل **ممنوع** أن يعتمد على "ذكائه" وحده. لكل مرحلة أدناه **قائمة أدوات إلزامية محددة بالاسم** (من نفس الأدوات المذكورة في `CLAUDE.md` — لا أدوات وهمية)، ولا تُعتبر المرحلة منتهية دون **مخرجات طرفية (terminal output) فعلية** تثبت التنفيذ، وليس تقرير الوكيل عن نفسه.

**قاعدة صارمة تُكرَّر في كل مرحلة:**
> "لا تخبرني أنك انتهيت. أرِني ناتج الأمر الفعلي الذي يثبت ذلك."

## 3) المراحل التنفيذية (بالترتيب — لا تجاوز مرحلة قبل إغلاق بوابتها)

### المرحلة A — الجرد والفهم الكامل قبل أي تعديل
**الهدف:** خريطة معرفية كاملة للمشروع بلا ثغرات فهم، قبل لمس أي سطر كود.

**الأدوات الإلزامية:**
- `Understand-Anything` → `/understand` على كامل المستودع لبناء خريطة معمارية.
- `claude-mem` → استرجاع قرارات وجولات سابقة (الجولات 1-78) لتجنّب تكرار عمل مُنجز أو نقض قرار سابق بدون سبب.
- `ast-grep-mcp` → بحث بنيوي (وليس نصيًا) عن أنماط متكررة في `src/components` و `src/app` (مكوّنات تُعيد تنفيذ نفس المنطق بأسماء مختلفة — التكرار الحقيقي غالبًا في المنطق لا في أسماء الملفات).

**بوابة الخروج:** تقرير جرد يذكر: عدد المكوّنات الفعلي المفحوص، أي منطق مكرر وجده ast-grep بالمسارات الدقيقة، وقائمة كل صفحة (34 صفحة) بحالتها الحالية.

### المرحلة B — توحيد نظام الثيم والألوان (إغلاق الفجوة #1 و #2 بدقة)
**الهدف:** كل لون في المشروع يمر عبر توكِنات `globals.css`، صفر استثناءات، بلا كسر بصري.

**نطاق العمل المحدد (من الفحص أعلاه، وليس عامًا):**
1. الملفات الـ18 التي فيها ألوان Tailwind خام (القائمة أعلاه) — كل لون دلالي (نجاح/فشل/تحذير) يجب أن يُستبدل بمتغير دلالي في `globals.css` (`--success`, `--destructive`, إلخ) لا بلون Tailwind مباشر.
2. الملفات الـ14 التي فيها hex ثابت — تحويل كامل لمتغيرات CSS.
3. أولوية قصوى: `PaymentDialog.tsx` — لأنها شاشة الدفع الفعلية التي يراها العميل وقت اتخاذ قرار الشراء؛ أي تشوه هنا يضرب الثقة مباشرة قبل الدفع.

**الأدوات الإلزامية:**
- `impeccable` → `/impeccable audit` قبل البدء (خط أساس)، ثم `/impeccable polish` بعد كل ملف، ثم `/impeccable critique` نهائيًا على كامل `src/`.
- `ui-ux-pro-max` → لاختيار/التحقق من القيم الدلالية الصحيحة للألوان (نجاح/خطأ/تحذير) بدل اختراعها.
- `axe-core` → إعادة فحص تباين الألوان (contrast) بعد كل تعديل — تغيير لون قد يكسر WCAG AA.

**بوابة الخروج (إثبات لا تقرير):**
```
grep -rE "(bg|text|border)-(red|blue|green|yellow|purple|pink|indigo|gray|slate|orange|teal|cyan)-[0-9]{2,3}" src/components src/app --include="*.tsx" | wc -l
# يجب أن يكون الناتج: 0 (أو مبرَّر كتابيًا لكل استثناء متبقٍ)
grep -rEl "#[0-9a-fA-F]{6}" src/components src/app --include="*.tsx" | wc -l
# يجب أن يكون الناتج: 0
```
+ لقطات شاشة فعلية (screenshot) لكل صفحة بوضعين: Light و Dark، RTL — وليس وصفًا نصيًا لها.

### المرحلة H — قسم العرض السينمائي للأصناف المميزة (مرجع: street-flavor.kimi.page)
**القرار المعتمد:** قسم استعراضي سينمائي لأبرز 3-5 أصناف أعلى صفحة `/menu/[slug]`، مع بقاء الشبكة الكاملة (`MenuItemCard.tsx` الحالي) أسفله دون تعديل لبقية الأصناف. **هذا القسم إضافة، وليس استبدالًا لطريقة العرض الحالية.**

**سبب وضعها هنا في الترتيب:** تعتمد على نظام التوكِن الموحَّد من المرحلة B (لا يجوز أن تُدخل ألوانًا خامًا جديدة بعد أن وحّدنا الثيم)، ويجب أن تكتمل **قبل** المرحلة C لأن مصفوفة اختبار الرحلة الكاملة يجب أن تُغطّي هذا القسم الجديد أيضًا.

**ما هو مؤكَّد بالفحص المباشر لهذا المشروع تحديدًا (لا افتراض):**
- `MenuItem` في `prisma/schema.prisma` **لا يملك حاليًا** أي حقل "مميز" (`isFeatured`) — تحقَّق من عدم الخلط مع `Restaurant.featuredRank` الموجود فعلًا (ذاك خاص بتمييز *مطاعم* على الصفحة الرئيسية، ليس أصنافًا داخل منيو واحد). **يجب إضافة migration جديد.**
- `MenuItem.dietaryTags String[]` موجود فعلًا لكنه دلاليًا لمعلومات غذائية (نباتي/خالي غلوتين) — **لا يُستخدم كبديل** لشارات النكهة الوصفية (Crunchbite/Melty/Smashed في الموقع المرجعي)؛ إن أراد المالك شارات وصفية فهي حقل جديد منفصل (`showcaseTagAr`/`showcaseTagEn` مثلًا) أو تُشتق تلقائيًا من `name`/`description` — **قرار يُترك للمرحلة A من التنفيذ الفعلي (الجرد)، لا يُخترع هنا**.
- `MenuItem.image String` موجود — صورة واحدة لكل صنف، كافية للصورة المركزية بالظل الدرامي (drop shadow) — **لا حاجة لحقل جديد هنا**.
- **لا يوجد** في المشروع أي مكتبة صور أيقونات مكوّنات (ingredients) لكل صنف. الموقع المرجعي يعرض أيقونات مكوّنات عائمة حقيقية (جبن، طماطم، ريحان...) لكل منتج. **حظر صريح على الوكيل:** ممنوع اختراع أو توليد صور مكوّنات وهمية لا تطابق الصنف الفعلي. البديل الصادق: إما (أ) عناصر عائمة زخرفية عامة (شرارات/دوائر تدرّج بدل صور مكوّنات حقيقية)، أو (ب) رفع المالك يدويًا لصور مكوّنات مختارة لكل صنف مميز عبر حقل صورة إضافي اختياري — **قرار يُطرح على صاحب المشروع صراحة قبل التنفيذ، لا يُفترض تلقائيًا.**
- المكوّن الحالي `MenuItemCard.tsx` (345 سطر) يعرض الصنف داخل الشبكة العادية — **لا يُعدَّل**. القسم الجديد يُبنى كمكوّن منفصل تمامًا (مثال تسمية: `FeaturedShowcase.tsx`) يُستدعى أعلى `MenuPageClient.tsx` فقط.
- الموقع المرجعي يستخدم خطوط أجنبية (`Bagel Fat One`, `Poppins`) واتجاه LTR وأسهم تنقّل غير معكوسة. **المشروع عربي RTL بالكامل** (Rule 5 في `CLAUDE.md` تفرض RTL بلا تشوه) — الخط، والاتجاه، واتجاه سهمي التنقّل (يمين/يسار) **يجب أن تُعكَس بالكامل** لتناسب RTL، لا تُنسخ من الموقع المرجعي حرفيًا.
- الموقع المرجعي يستخدم صور PNG ضخمة غير مُحسَّنة (`hero-subway.png` بدون تحسين واضح) — المشروع فيه بالفعل مكوّن `OptimizedImage` مستخدَم في أماكن أخرى (مؤكَّد بالفحص في `admin/settings`) — **يُستخدم إلزاميًا هنا**، لا صور خام.

**نطاق العمل الدقيق:**
1. Migration: إضافة حقول التمييز على `MenuItem` (الاسم النهائي وعدد الحقول يُقرَّر في الجرد الفعلي — لا تُخمَّن بنية الحقول هنا).
2. واجهة إدارة: إضافة تحكّم "تمييز هذا الصنف + ترتيبه" داخل نموذج تعديل الصنف الحالي في `owner/menu` (المسار الدقيق للنموذج **يُكتشف في المرحلة A/الجرد قبل التعديل** — لم يُفحص في هذه الجلسة).
3. مكوّن العرض: `FeaturedShowcase.tsx` جديد — مشهد كامل لكل صنف مميز (اسم كبير كخلفية بلون من توكِن الثيم لا لون خام، صورة الصنف بظل، شارات نصية، وصف قصير، سهمي تنقّل RTL-صحيحين).
4. حركة/انتقال بين المشاهد عبر Framer Motion (مكتبة موجودة أصلًا في المشروع — لا مكتبة جديدة).
5. احترام `prefers-reduced-motion` إلزاميًا — الموقع المرجعي لا يفعل هذا؛ مشروعنا يجب أن يفعل (معيار a11y أعلى).

**الأدوات الإلزامية:**
- `Understand-Anything` → تأكيد بنية `owner/menu` الفعلية قبل أي تعديل نموذج (لا تخمين).
- `impeccable` + `ui-ux-pro-max` → تصميم الألوان/الخطوط/التركيب من توكِنات المشروع، لا نسخ ألوان الموقع المرجعي حرفيًا.
- `axe-core` → فحص أن العناصر الزخرفية `aria-hidden`، وأن الأسهم قابلة للتنقل بلوحة المفاتيح.
- `ast-grep-mcp` → التأكد أن `FeaturedShowcase.tsx` لا يكرر منطق موجود فعلًا في `MenuItemCard.tsx` أو `GalleryCarousel.tsx` (كلاهما موجود ويُحتمل تشابه جزئي في منطق الكاروسيل — **يجب التحقق لا الافتراض**).

**بوابة الخروج (إثبات لا تقرير):**
- `npx prisma migrate status` يُظهر الـ migration الجديد مطبَّقًا فعليًا.
- لقطات شاشة فعلية لصفحة `/menu/[slug]` بالقسم الجديد: RTL، Light، Dark، 3 أحجام شاشة (نفس مصفوفة المرحلة C أدناه).
- فيديو قصير أو GIF فعلي يوضّح التنقّل بين الأصناف المميزة بالسهمين (ليس وصفًا نصيًا).
- تأكيد أن الشبكة الأصلية أسفل القسم الجديد **لم تتأثر إطلاقًا** (نفس عدد الأصناف، نفس السلوك، `git diff` على `MenuItemCard.tsx` = فارغ).

### المرحلة C — رحلة العميل الكاملة End-to-End (إغلاق الفجوة #5)
**الهدف:** عميل حقيقي يدخل → ينشئ حسابًا → يشترك → يدفع → يصل لخدماته — بدون توقف، بدون تكرار خطوة، بدون تشوه — على كل breakpoint وكل ثيم.

**مصفوفة الاختبار الإلزامية (لا يجوز تقليصها):**
- 3 أحجام شاشة: موبايل (375px)، تابلت (768px)، ديسكتوب (1440px)
- 2 ثيم: Light / Dark
- الاتجاه: RTL فقط (المشروع عربي بالكامل) — لكن تأكيد عدم وجود بقايا LTR مسربة (أيقونات معكوسة خطأ، هوامش mirrored بشكل خاطئ)
- المسار الكامل: `/` → تسجيل حساب → تسجيل دخول → `/pricing` → `/subscribe` (PlanSelector → PaymentSection → كل طريقة دفع: Libyana / Madar / تحويل بنكي) → `SuccessPanel` → لوحة `/owner` → إدارة المنيو (تمييز صنف عبر التحكّم الجديد من المرحلة H) → توليد QR → معاينة `/menu/[slug]` كعميل نهائي (**بما فيها القسم السينمائي الجديد من المرحلة H: التنقّل بالسهمين، الشبكة الكاملة أسفله سليمة**)

**الأدوات الإلزامية:**
- Playwright (موجود فعلًا في المستودع: `playwright.config.ts`, `tests/e2e`) — تشغيل فعلي، لا افتراض أن الاختبارات الموجودة كافية؛ يجب توسعتها لتغطي كل خلية من المصفوفة أعلاه إن لم تكن مغطاة.
- `gstack` → `/qa` و `/browse` للتحقق البصري الفعلي بالمتصفح، ليس فقط اجتياز assertions.
- `axe-core` على كل صفحة في المسار.

**بوابة الخروج:** ناتج تشغيل Playwright الفعلي (pass/fail لكل حالة في المصفوفة) + لقطات شاشة لكل خطوة × كل حجم شاشة × كل ثيم. أي خطوة فيها احتكاك (تحميل بلا مؤشر، رسالة خطأ غامضة، زر بلا تغذية راجعة بصرية) = فشل، ولا تُغلق المرحلة حتى تُصلح.

### المرحلة D — تحقق التكرار الفعلي عبر AST (وليس أسماء الملفات)
**الهدف:** التأكد أن "بدون تكرارات" تعني منطقًا فعليًا، لا مجرد ملفات بأسماء مختلفة.

**الأدوات الإلزامية:**
- `ast-grep-mcp` → قواعد بحث بنيوي عن: مكوّنات UI بنفس البنية الوظيفية بأسماء مختلفة (مثال محتمل: تعدد أزرار/بطاقات بمنطق شبه مطابق عبر `admin/`, `owner/`, `menu/`)، منطق تحقق (validation) مكرر بدل استيراد من مصدر واحد، استعلامات Prisma متشابهة يمكن توحيدها في `lib/`.
- `Understand-Anything` → `/understand-diff` لمقارنة البنية قبل/بعد كل دمج.

**بوابة الخروج:** قائمة صريحة (بمسارات دقيقة) بكل تكرار حقيقي وُجد + تأكيد أن الدمج لم يكسر أي اختبار (`npm run typecheck && npm run lint && next build` بنواتج فعلية = 0 أخطاء، ليس تصريحًا).

### المرحلة E — مصادر خارجية مفتوحة المصدر كمرجع جودة (وليس نسخًا)
**الهدف:** تنفيذ ما طلبته صراحة — الوكيل لا يعمل بذكائه المجرد فقط، بل يقارن حلوله بمشاريع مفتوحة المصدر ناضجة قبل أن يعتبر تصميمه "نهائيًا".

**تعليمات دقيقة للوكيل (لتفادي انتحال تصميم محمي):**
- يُسمح بدراسة الأنماط المعمارية/التفاعلية (مثال: كيف تُبنى صفحات pricing/checkout الاحترافية في مشاريع SaaS مفتوحة المصدر مشابهة على GitHub) لاستخلاص مبادئ (تسلسل الخطوات، حالات التحميل، رسائل الخطأ) — **وليس نسخ كود أو تصميم بصري حرفيًا**.
- كل استلهام يُوثَّق: من أين، وما الذي طُبِّق فعليًا بأسلوب Smart Menu الخاص (الألوان/الخطوط/الهوية العربية RTL يجب أن تبقى مميزة وليست تقليدًا).
- استخدام `ui-ux-pro-max` (79 نمط، 192 لوحة ألوان، 74 خط) كمرجع أول قبل أي بحث خارجي — لأنه مصمّم لهذا الغرض بالضبط.

**بوابة الخروج:** ملف قصير (`docs/design-references-round79.md` أو مشابه) يوثّق كل استلهام + المصدر + كيف طُبِّق بما يخدم هوية Smart Link تحديدًا.

---

### المرحلة F — الأمان والخصوصية (إغلاق البند المعلَّق من قبل)
**تذكير بما هو معلَّق أصلًا (من سياق سابق، ليس من هذا الفحص):** تدوير كل الأسرار المتبقية وجعل مستودع GitHub خاصًا (private) كخطوة أخيرة قبل الإطلاق الفعلي/الإعلانات.

**الأدوات:** `gstack /security` + مراجعة يدوية لـ `.env` وسجل git (`git log -p` بحثًا عن أسرار قديمة مكشوفة تاريخيًا حتى لو أُزيلت لاحقًا — git history يحتفظ بها ما لم يُعاد كتابة التاريخ).

**بوابة الخروج:** تأكيد فعلي (ليس وعدًا) أن كل مفتاح API/سر تم تدويره، ثم تحويل المستودع لخاص.

---

### المرحلة G — المراجعة النهائية متعددة الوكلاء (Ruflo swarm) قبل أي إعلان "جاهز"
طبقًا لما هو مفروض أصلًا في `CLAUDE.md` (Ruflo كنظام تنفيذ افتراضي)، هذه المرحلة تُفعِّله فعليًا لا نظريًا:
- عمارة (architect) + أمان (security) + أداء (performance) + اختبار (test) + تصميم (design review عبر `gstack /design-review`) — كل دور يراجع بشكل مستقل، ولا تُعتبر المرحلة منتهية حتى تمر كل المراجعات بلا نتائج CRITICAL أو HIGH.
- مخرج نهائي واحد: تقرير جاهزية إطلاق (Launch Readiness) يحوي: حالة كل مرحلة أعلاه (A-F) بدليلها، لا بوصفها "تم".

## 4) قاعدة الإثبات (تنطبق على كل مرحلة أعلاه بلا استثناء)
لكل مرحلة، الوكيل يُطالَب بأحد الإثباتات التالية فقط — لا شيء غيرها يُقبل:
- ناتج أمر طرفي فعلي (`npm run build`, `npm run test`, `grep` count, إلخ) مُلصَق حرفيًا.
- لقطة شاشة فعلية للصفحة/الحالة المعنية.
- رابط/معرّف تقرير أداة (axe-core report, Playwright report) قابل للفتح.

**أي جملة من نوع "تم الانتهاء بنجاح" أو "كل شيء يعمل الآن" بدون أحد الإثباتات أعلاه = مرفوضة تلقائيًا وتُعاد المرحلة.**

## 5) الترتيب الموصى به للتنفيذ (قرار حاسم واحد، لا خيارات)
A → B → D → H → C → E → F → G

**السبب:** يجب فهم المشروع (A) وتوحيد الثيم (B) وحذف التكرار المنطقي (D) **قبل** بناء القسم السينمائي الجديد (H) — حتى يُبنى مباشرة بالتوكِنات الموحَّدة وبدون تكرار منطق كاروسيل موجود مسبقًا. القسم الجديد (H) يجب أن يكتمل **قبل** اختبار الرحلة الكاملة (C) لأن مصفوفة C يجب أن تغطّيه. الاستلهام الخارجي (E) يأتي بعد استقرار البنية لا قبلها. الأمان (F) والمراجعة الجماعية (G) دائمًا آخر خطوتين قبل الإطلاق.
