## 2) الإصلاح الهيكلي الكبير — قابلية إعادة تشغيل الهجرات

**المشكلة بجذرها:** مشروع بدأ بـ `db push` ثم انتقل للهجرات تدريجيًا، فبقيت كائنات كاملة خارج السلسلة. أي قاعدة جديدة (CI، استعادة كوارث، بيئة مطوّر) كانت تنكسر، بينما الإنتاج يعمل لأن كائناته خُلقت تاريخيًا خارج الهجرات.

**الحل المعماري (بلا جراحة تاريخ):**
1. `0_zz_replayability_prereq` — **مبكرة الترتيب معجميًا** (`0_init` < `0_zz_` < `10_` < `1_`): تنشئ المطلوبات الثلاث (enum `SubscriptionStatus` بلا EXPIRED — تضيفها الهجرة 8؛ عمود `User.subscriptionStatus`؛ جدول `TelegramApprover` بصيغته النهائية BIGINT) — كل الجمل محروسة.
2. `11_replay_parity` — **مطاردة الانزياح الكامل**: كل ما في `schema.prisma` وغاب عن السلسلة (5 جداول، 21 عمودًا، 16 فهرسًا، 8 مفاتيح، قيم Role، تبديل `SystemEvent.severity` النوعي بشرط فحص `udt_name` حتى لا تُمس بيانات الإنتاج أبدًا).
3. `migration_lock.toml` — كان مفقودًا (إدارة يدوية تاريخية).

**حراسة الإنتاج (نقطة التصميم الحاسمة):** لا يمكن تعديل هجرات مطبَّقة (checksums)، لذا كل جملة جديدة محروسة (`IF NOT EXISTS` / كتل DO بـ duplicate_object / شروط فحص الكتالوج) — على الإنتاج: **no-op رياضيًا**، وعلى قاعدة طازجة: **التكامل الكامل**. أُثبت بالاثنين معًا.

**بوابة القبول الحرفية:**
```
$ npx prisma migrate diff --from-migrations prisma/migrations --to-schema prisma/schema.prisma --script --exit-code
-- This is an empty migration.
EXIT: 0
```

## 7) دروس معمارية وثّقت للجيل القادم

1. **ترتيب الهجرات معجمي** (`0_zz_` قبل `1_`): التسمية أداة تحكم في الترتيب — استُغلت هنا بوعي.
2. **standalone = عملية جديدة**: بيئة وقت البناء لا تنتقل — كل متغير يتحقق منه `env.ts` وقت التشغيل يجب أن يكون في بيئة الخادم.
3. **اختبارات المرآة** (دوال معاد تعريفها داخل الاختبار) لا تحمي من انحراف الإنتاج — حدّثت المرآة لتطابق الواقع ووثّقت السبب.
4. **503 للإعداد الناقص = كشف معلومات**: الإغلاق الموحّد 403 هو الوضع الصحيح أمنيًا.
5. **سكربت بذر بلا مصادقة** (KDF مطابق) يحل معضلة CI بلا فتح أي باب إنتاجي.
