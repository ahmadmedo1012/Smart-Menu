# تقرير تفتيش الجولة 93 — الوكيل 1-c «مدقق سلامة البيانات»

**النطاق:** مسارات المال (طلبات/اشتراكات/إحالات/ولاء)، حدود الخطط، المعاملات، الوظائف الدورية، سلسلة الهجرات، الحذف وPII، اتساق seed.
**المنهج:** قراءة كود HEAD بأدلة ملف:سطر + استعلامات قراءة فقط على قاعدة الجولة المحلية (localhost:5434/smartmenu) + تحقق كتالوج القيود/المشغّلات في pg_constraint/pg_trigger + `prisma migrate status/diff` (كلاهما قراءة فقط). **لم يُعدَّل أي كود ولم تُكتب أي صفحة في قاعدة البيانات.**

---

## خلاصة تنفيذية

خط الدفاع المالي الأساسي **سليم بنيويًا**: كل مسارات السقوف (طلبات/أصناف/منيوهات/إحالات) تُنفَّذ داخل `$transaction` مع قفل `FOR UPDATE` على صف المالك للسقف ثم العدّ ثم الإنشاء (نمط r92 المطلوب)، والمنح المالي (ولاء/إحالات) مقيّد بقلوب شرطية idempotent، والدفعات المعلقة محمية بفهرس فريد جزئي على مستوى قاعدة البيانات. أنواع المال كلها `Decimal(10,2)` (لا `Float` في المخطط إطلاقًا) والنقاط `Int`.

وجدتُ **2 عيوب عالية الخطورة** (حذف المطعم يفشل عند وجود تقييمات بسبب `Restrict` في مسار الـcascade؛ مسار `/api/seed` يعيد إدخال كذبة «أصناف غير محدودة» التي أصلحتها r92)، **4 متوسطة**، وعددًا من الملاحظات الدنيا — كلها بأدلة.

## 1) عيوب عالية الخطورة [HIGH]

### H-1) حذف المطعم يفشل نهائيًا متى وُجد تقييم واحد على أي صنف (مسار مالك + مسار أدمن)
**الأدلة:**
- `prisma/schema.prisma:504` — `Review.menuItem` بـ `onDelete: Restrict` (ومثله `OrderItem.item` بـ Restrict عند `:251`). لا يوجد أي مسار API يحذف تقييمًا (تحقق rg: لا وجود لـ `prisma.review.delete` في src).
- كتالوج القاعدة (قراءة فقط): `Review_menuItemId_fkey` confdeltype=`r`، `OrderItem_itemId_fkey`=`r`، وترتيب مشغّلات الحذف المتتالية على جدول Restaurant حسب OID: ق cascade التصنيفات (16916) يسبق ق cascade الطلبات (17219 — أُعيد إنشاؤه بالهجرة 11 من RESTRICT إلى CASCADE)، ومشغّلات Restrift على MenuItem (17224 للطلب، 17254 للتقييم) تُصف في ذيل قائمة after-trigger FIFO.
- عند `DELETE FROM "Restaurant"`: الأصناف تُحذف عبر مسار التصنيفات **قبل** حذف الطلبات/بنودها (التي تسلك قائمة FIFO لاحقًا فتنجو بنود الطلبات من فحص Restrict)، لكن **التقييمات لا يحذفها أي مسار إطلاقًا** → فحص `Review_menuItemId_fkey` الفوري يفشل → إجهاض الحذف كله.
- المساران المتأثران: `src/app/api/owner/restaurants/[id]/route.ts:117` (`tx.restaurant.delete` مباشرة — حذف منيو ثانوي لمالك) و`src/app/api/restaurants/[id]/route.ts:257` (حذف أدمن). الخطأ يظهر كـ P2003 → `handleError` يعيد 400 «بيانات مرتبطة لا يمكن حذفها» (`src/lib/api-helpers.ts:116-118`).

**السيناريو المُضر:** مطعم تشغيلي لديه تقييم عميل واحد على صنف واحد → المالك يريد حذف منيو فرعي/الأدمن يريد حذف المطعم → 400 دائم، المطعم غير قابل للحذف عبر أي API (لا يوجد حتى مسار لحذف التقييمات يدويًا). البيانات سليمة (الحماية تعمل) لكن الوظيفة الحذف مكسورة بصمت.
**المقترح:** داخل معاملة حذف المطعم: احذف/جهّل التقييمات صراحة قبل `restaurant.delete` (مثل `tx.review.deleteMany({ where: { menuItem: { category: { restaurantId } } } })`)، أو اجعل `Review.menuItem` بـ `SetNull`/Cascade مقصودًا مع تعليق يوثّق القرار، وأضف اختبار انحدار e2e «حذف مطعم لديه طلب + تقييم» (لا يوجد اليوم — فحصت مواصفات e2e: تُنشئ تقييمات لكن لا تحذف مطعمًا لديها). **تنبيه تحقق:** مسار بنود الطلبات ينجو بسبب ترتيب قائمة المشغّلات FIFO — سلوك حساس لترتيب OIDs ويستحق اختبارًا عمليًا يثبّته.

### H-2) مسار `POST /api/seed` يعيد إدخال وعد «أصناف غير محدودة» الذي أصلحته r92 (تناقض نص/سقف مالي)
**الأدلة:**
- `src/app/api/seed/route.ts:9` — Premium: `maxItems: 9999` مع features تحوي **«أصناف غير محدودة»**.
- `scripts/ci-seed.mjs:45-52` — نفس الخطة بالنص المصحح **«أصناف حتى 9999»** مع تعليق يصرّح أنه «Same defaults as /api/seed route» (لم يعودا متطابقين).
- هجرة `prisma/migrations/20260907_round92_plan_texts/migration.sql` (r92 A3+A4) صحّحت الوعد في البيانات الحية، واختبار `tests/unit/r92-plan-texts.test.ts:22` يثبّت **نص ci-seed فقط** — نسخة `/api/seed` غير مرئية للاختبار.
- `/api/seed` يعمل upsert (`route.ts:26-31`) — أي تشغيل له (في dev، أو production مع `ALLOW_SEED=true`) **يكتب فوق** النص المصحح ويعيد التناقض: الصفحة تعد «غير محدودة» بينما `PlanLimitError` يوقف العميل عند 9999 (نوع النزاعات الموثقة في r92).

**السيناريو المُضر:** بيئة تُبذر عبر API (أو إعادة بذر dev بعد هجرة r92) → تُعاد المشكلة التجارية المُصلحة، بصمت، لأن الهجرة نفسها no-op على قاعدة فارغة (الخطط تُزرع بعدها).
**المقترح:** وحّد المصدر: صدّر `DEFAULT_PLANS` من مكان واحد (ci-seed) واستورده في المسار، أو انسخ النص المصحح؛ وأضف اختبارًا يقرأ نص المسار (النموذج الحالي يغطي نصف الحقيقة فقط).

- `api/cron/subscription-expiry`: يوميًا `0 1 * * *` (vercel.json:9) ✓؛ يقلب PAID→EXPIRED لمن انتهى أي منيو له (يتطابق دلاليًا مع `min(planEnd)` في الحارس الكسول `subscription-guard.ts:44-47`) ✓.

### المخطط والهجرات:
- أنواع المال كلها `Decimal(10,2)` (price/discountedPrice/subtotal/discount/total/totalSpent/amount/priceDelta/avgRating) والنقاط/الكميات `Int` — **لا Float إطلاقًا** ✓ (خطر الفاصلة العائمة غير موجود في التخزين).
- قيود فريدة حاسمة موجودة: `Order.orderNo` (idempotency)، `LoyaltyCard(customerPhone, restaurantId)` (منع ازدواج البطاقة)، `LoyaltyCard.referralCode`، `Referral(referralCode, referredName)` (منع ازدواج المطالبة)، `RateLimitEntry(key, windowEnd)`، فريد جزئي pending-payment، `Restaurant.slug`، `SubscriptionPlan.name`، `Setting(restaurantId,key)`، `WhatsappTemplate(restaurantId,name)`.
- سلوك الحذف الموثّق (مقاسًا على كتالوج القاعدة): حذف مطعم = cascade كامل (طلبات، بنود، بطاقات ولاء، إحالات، حركات مكافآت، إعدادات، قوالب واتساب، روابط) — **مع استثناء H-1 (التقييمات)**؛ حذف صنف = ممنوع إذا له طلبات/تقييمات (Restrict مقصود لحفظ لقطات الأسعار، يُعرض 400 نظيف عبر handleError)؛ حذف مستخدم = جلساته cascade، سجلات التدقيق والدفعات تُحفظ (SetNull) — مسار المال محفوظ.
- سلسلة الهجرات: 22 هجرة طُبقت على قاعدة فارغة بنجاح كامل (`migrate status`: «Database schema is up to date!»)؛ **`migrate diff` قاعدة↔مخطط = لا فرق (صفر انحراف)** ✓؛ هجرة r92 للنصوص idempotent فعلًا (حراسة LIKE + حراسة السقف + مفاتيح بالأسماء لا ids — مثبتة باختبار r92-plan-texts) ✓؛ لا تعارض أسماء فهارس (هجرة 13 حتى أزالت المكررات المدعومة بـ unique)؛ الهجرات القديمة غير المحروسة (6/8/13/14) تعمل مرة واحدة في السلسلة المسجلة ونجحت في الإعادة.
- **onDelete في المخطط مقابل القاعدة: متطابقان** (تحقق pg_constraint: كل c/r/n يطابق schema.prisma).

### اتساق العدادات مقابل السجلات:
- إستراتيجية «زيادة مباشرة داخل معاملة + صف سجل في نفس المعاملة» (لا إعادة حساب من السجلات): النقاط (earn/redeem)، totalOrders/totalSpent، avgRating/ratingCount (`items/[id]/reviews/route.ts:157-167` — بيان SQL ذري واحد يحل T4 lost-update). حاليًا **صفر انحراف** (استعلامات المطابقة card.points↔SUM(tx) وratingCount↔COUNT(review) — قاعدة الجولة فارغة عدا المدير والخطتين).
- إحصاءات لوحة المالك: تجميع مباشر من Order/OrderItem — **لا يوجد جدول AnalyticsEvent أصلًا** (المخطط لا يحويه) — أي قيم اللوحة مشتقة من مصدر الحقيقة نفسه، مع ملاحظة M-4 (فلتر الحالة).
- حالة الرصيد الحالية للبطاقات تُعرض من العدّادات (`loyalty/stats:36-93` قراءة مباشرة).

### GDPR-like (ملخص ما يُحذف وما يبقى):
- **يُحذف:** صف المستخدم (username/password/name/email/phone/telegram*)، الجلسات (cascade)، وعند حذف مطعم: طلباته وبيانات عملائه وبطاقات الولاء وحركاتها وقوالب واتساب (cascade) + الصور من blob بعدها (`restaurants/[id]:273-279`).
- **يبقى:** AuditLog (90 يومًا ثم كرون التنظيف) بأسماء مستخدمين في metadata؛ SubscriptionPayment **للأبد** (سجل مالي، مع tempUsername/receipt في metadata)؛ PII العملاء (Order/LoyaltyCard/Review/Referral) بلا مسار محو فردي ولا سياسة احتفاظ (Review لا تُحذف أصلًا — H-1).
- ترميز IP في الإحالات: بصمة sha256 لا IP خام (`referral-conversion.ts:64-68`) ✓.

### seed مقابل schema:
- `ci-seed.mjs`: نصوص مصححة ✓ idempotent (upsert بالاسم؛ المدير لا يُمس) ✓؛ القاعدة المحلية مثبتة بالنص المصحح («أصناف حتى 9999») ✓ — **لكن `/api/seed` منحرف (H-2)**. لا يوجد `prisma/seed.ts` (البذر عبر scripts/API).
