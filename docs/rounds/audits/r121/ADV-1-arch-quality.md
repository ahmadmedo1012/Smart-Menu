### ADV-1-2 [P3] New `SubscriptionExpiryBanner` renders Date-dependent text during SSR + hydration — a hydration-mismatch window
- Type: FACT (code-path verified)
- Evidence: `src/app/(protected)/owner/OwnerShell.tsx:67-71` — `getPlanDaysRemaining(planEnd, now: Date = new Date())`; called at `:89` inside `SubscriptionExpiryBanner`, which OwnerShell renders unconditionally (`:263`). The new server layout (`owner/layout.tsx:48-60`) SSRs this client component, so the banner's day-count text («اشتراكك ينتهي خلال 7 أيام» vs «…6 أيام») is computed once with the **server clock** (initial HTML) and again with the **client clock** (hydration). When the two straddle a day boundary — planEnd landing within the server/client clock delta, or a skewed client clock — React 19 logs a hydration text mismatch and re-renders the subtree. Self-healing, rare, but it is the one Date-in-render hazard the IMPL-3 refactor introduces.
- Contrast (clean): the role/permissions path has NO such hazard — `AccessGateMeProvider` is fed serializable props (`AdminShell.tsx:100-103`), the gate resolves synchronously on both sides from context (`useAccessGate.ts:48-50`), zero mismatch. This banner is the only offender.
- Fix (minimal): resolve `days` server-side in `owner/layout.tsx` (it already computes planEnd there) and pass it down as a prop — or compute it in a `useEffect` and render nothing on the first pass (the banner is a toast-class affordance; one-frame delay is invisible).
- Risk: none; unit tests already pin `getPlanDaysRemaining` with an explicit `now`, so they are unaffected.

### ADV-1-3 [P3] `plans-server.ts` "single server-side plans fetch" overstates: /api/plans keeps a second cache + a different mapping; /pricing worst-case staleness doubles
- Type: FACT
- Evidence:
  - `src/lib/plans-server.ts:16-17` (module cache, TTL 300s, explicit `Plan[]` mapping, `Number(p.price)`) vs `src/app/api/plans/route.ts:6-7` (its own independent module cache, TTL 300s, spread mapping that serializes `price` as a Decimal-string and leaks `isActive`/timestamps). Both r121 pages' client fallbacks (`PricingClient.tsx:219`, `SubscribeClient.tsx:99,127`) still consume the /api/plans shape. The helper's header ("the single server-side plans fetch … without inventing a second data layer") and the subscribe page's comment ("the SAME helper /pricing uses") are true for the two SSR pages but read as if the plans data layer is now one — it is two, with independent staleness windows and different row mappings. The split itself is pre-existing (the round didn't reintroduce drift); the NEW part is the overstated-unification framing + the layering below.
  - Behavior delta on /pricing (new): previously each ISR regeneration (`revalidate = 300`, pricing/page.tsx:11) re-queried the DB → max staleness ≈ 5 min. Now a regeneration can hit the helper's module cache → worst case ≈ **10 min**. Deliberate per the helper's design note, but the doubling on the public pricing surface is nowhere stated.
- Impact: an admin plan edit can be visible on /api/plans (fallback) up to ~5 min before/after the SSR pages show it (two unsynchronized TTLs). Low-stakes (plans mutate rarely) but it is precisely the dual-data-layer drift class the task asked about.
- Fix: either route `api/plans/route.ts` through `getActivePlans()` (one cache, one mapping — its response shape grows the missing fields or keeps a spread on top of the helper's output), or add one sentence to plans-server.ts's header owning the second cache's existence + the 10-min bound.
- Risk: low; /api/plans consumers are the two fallback fetches (both `Number()`-guarded) and e2e api-smoke.
