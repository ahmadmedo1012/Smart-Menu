## Findings

### ADV2-1 [P2] Webhook self-approval guard keys on the payer's *linked* telegram chat — an approver whose payer account has no/different link still self-approves via Telegram
- Type: FACT (code-proven identity split; exploit premise = configured Telegram approver who also holds a platform account)
- Evidence: `src/lib/subscription-decisions.ts:70-80` — `isPaymentSelfApproval` returns `Boolean(chatId) && String(chatId) === String(approverTelegramId)` where `chatId = payment.user.telegramChatId`. If the payer's User row has **no linked chat** (or a different personal chat than the one they use as approver), the guard is a no-op. `src/app/api/telegram/webhook/route.ts:53-101` — the only gates are (1) `getAdminTelegramIds()` allowlist (`src/lib/telegram-admin.ts:3-20`: `TELEGRAM_ADMIN_IDS` env + `TelegramApprover` table — no userId on that model, `schema.prisma:291-300`) and (2) this telegram-id-match. **No userId comparison anywhere on the webhook path.** The r121-E2 panel twin (`src/app/api/admin/subscriptions/route.ts:80-86`) does compare `selfPayment.userId === auth.userId` — the correct identity key — but only closes the panel. `TelegramApprover` has no user relation, so the webhook cannot map approver→account except via `User.telegramChatId`, which the payer controls (linking is voluntary — `admin/telegram/verify`, `admin/profile`).
- Impact: exact insider class r118-A2-P2 was written to close («sub_admin يضيف معرّفه ثم يوافق على طلب اشتراكه المدفوع»): a Telegram approver (env list or TelegramApprover row) who files a paid upgrade from a platform account whose `telegramChatId` is unlinked/different receives the approval keyboard (audience = approvers) and taps 🟢 → `isPaymentSelfApproval` = false → `resolveSubscriptionPayment(verified)` → paid plan activated, no money moved. No MANAGE_SUBSCRIPTIONS needed for the webhook path.
- Fix (minimal): extend the guard to be userId-aware — in `isPaymentSelfApproval` (or a second check in the webhook), also block when a `User` with `telegramChatId === String(approverTelegramId)` has `id === payment.userId` *or* when the payment's `userId` belongs to a staff-role account and the approver telegram id maps to that same staff account's approver entry. Pragmatic alternative: refuse to broadcast keyboards (or to accept webhook decisions) for payments whose `user.role ∈ {admin, sub_admin, super_admin}` — staff-filed payments routed to the panel only, where the userId guard is airtight.
- Risk: of fixing — low (adds one lookup on a rare path; legit staff-paid upgrades still resolvable by a *different* super_admin from the panel). Of not fixing — the webhook half of the self-approval hole stays open for the trusted-approver set; the r121-E2 fix is incomplete as a pair.
- Tests required: unit — approver telegram id ≠ payer account's unlinked chat → webhook callback on own payment → blocked toast, payment stays pending; payer with linked chat → still blocked (regression); third-party approver → allowed.

### ADV2-2 [P3] `zz_round121_orderitem_effective_price_backfill` is NOT idempotent — the comment claims it is, and a manual re-apply silently double-charges history
- Type: FACT (empirically proven on the round DB, rollback-only)
- Evidence: `prisma/migrations/zz_round121_orderitem_effective_price_backfill/migration.sql:16-19` claims «The cutoff is ALSO the idempotency guard: re-running … those are re-set to the same value (no marker column needed)». The UPDATE at :38-54 is `SET price = price + Σdeltas` over rows still matching the cutoff — the WHERE has no marker on the *current* value, so a second application adds the deltas **again**. Proven locally (synthetic pre-cutoff order + `priceDelta:2.5` row, inside BEGIN…ROLLBACK): run 1 → 10.00→12.50 (correct), run 2 → 12.50→15.00 (double-count). The sibling migration `zz_round121_check_constraints` explicitly advertises hand re-apply as safe («safe to re-apply by hand (self-healing)»), inviting exactly this mistake on the backfill file.
- Impact: `prisma migrate deploy` runs each folder once, so normal deploys are safe; but any manual re-apply, `migrate resolve`+re-deploy mistake, or copy-paste into Neon console silently corrupts historical OrderItem prices (receipts/stats read Order.total, so damage is display-level on receipts, not billing).
- Fix (minimal): correct the comment (state plainly: NOT idempotent — never re-apply), or make it actually idempotent (e.g. bound the UPDATE to rows whose order predates the cutoff *and* whose price still equals base — impractical without a marker; the honest fix is the comment).
- Risk: of fixing — none (doc-only). Of not fixing — an operator following the file's own claim corrupts financial history.
- Tests required: none (comment fix); if SQL changed — a re-apply double-run assertion in the migration's test harness.

### ADV2-3 [P3] cancelled→completed still possible via a read-then-write race on the plain-update path (terminal guard checks a stale snapshot)
- Type: FACT (race window; narrow preconditions)
- Evidence: `src/app/api/orders/[id]/route.ts:116-118` — the r121-D2 guard evaluates `existing.status` read at :79. The loyalty-accrual block (:134-232) is race-safe (conditional `updateMany … where status = existing.status` at :165-168 + RewardTransaction earn-row check), but the **plain update at :244-251 is unconditional** (`prisma.order.update({ where: { id }, data: body })`). Sequence: staff A reads order (status `ready`, total < 10 → `ptsEarned = 0`, or no `customerPhone`); staff B cancels; A's request proceeds past the guard (stale snapshot says `ready`) and past the accrual block (pts=0/phoneless skip) → :244 flips the cancelled row to `completed`. The referral hook at :255-262 then fires on cancelled revenue if a phone exists (in-memory `existing.status !== 'completed'` still true).
- Impact: a cancelled order can be re-opened as completed (and a referral converted) when two privileged staff race cancel-vs-complete on the same low-value order. Loyalty minting itself stays protected (accrual block's conditional update + earn-row guard). Requires ≥2 staff, same restaurant, same order, sub-second window, total<10 LYD or anonymous order — LOW practical likelihood, but the guard's stated invariant («cancelled is TERMINAL») is not airtight.
- Fix (minimal): make the bottom update conditional like the accrual block — `order.updateMany({ where: { id: oid, status: { not: 'cancelled' } }, data: body })` and re-read on count=0 (mirrors :165-175).
- Risk: of fixing — low (same-status/notes PUTs unaffected; `whatsappSent` toggles unaffected). Of not fixing — terminal-state invariant holds only for non-racing writers.
- Tests required: unit — concurrent cancel+complete with mocked sequencing: plain path cannot land `completed` on a cancelled row.

### ADV2-4 [P3] r121 migrations take full-lock DDL on prod-Neon tables of unknown size, and the CHECK migration runs BEFORE the backfill that could violate it
- Type: FACT (Postgres DDL semantics + prisma lexicographic ordering)
- Evidence: `zz_round121_check_constraints/migration.sql:31-47` — six `ADD CONSTRAINT … CHECK` **without `NOT VALID`**: Postgres takes ACCESS EXCLUSIVE on MenuItem/OrderItem/Review/LoyaltyCard/RewardTransaction and full-scans each while holding it. `zz_round121_not_null_alignment/migration.sql:24-34` — `SET NOT NULL` on Restaurant/User/MenuItem×2 (same lock class; local DB: 0 NULL rows, no-op — but prod unverified). Folder order (lexicographic, prisma migrate deploy): `zz_round121_check_constraints` < `zz_round121_not_null_alignment` < `zz_round121_orderitem_effective_price_backfill` — so the OrderItem `price >= 0` CHECK is live **before** the backfill's `price = price + Σdeltas` runs; a pre-r120 row whose base + negative-delta sum < 0 (r118-A3-P1's negative-effective-price rejection postdates such rows) would make the backfill UPDATE violate the CHECK → migration aborts mid-deploy (transactional — no corruption, but a stuck deploy). Backfill is otherwise properly bounded: `Order.createdAt < '2026-09-25 17:37:05'` cutoff + `modifiersJson LIKE '[%'` + numeric-regex delta filter (verified locally: 0 pre-cutoff modded rows, 66 total OrderItems — Neon needs its own count).
- Impact: on large prod tables the CHECK/NOT-NULL scans hold ACCESS EXCLUSIVE for the scan duration (writes block); a legacy negative-sum row aborts the deploy. No data-loss/destruction anywhere in the diff (all four migrations additive except the one constraint drop).
- Fix (minimal, ops): on Neon pre-flight, run the documented COUNT checks INCLUDING a would-be-negative backfill probe (`SELECT … WHERE base + Σdeltas < 0`); if any large table, prefer `ADD CONSTRAINT … NOT VALID` + `VALIDATE CONSTRAINT` (SHARE UPDATE EXCLUSIVE) as a follow-up pattern for future rounds — for THIS round, shipping as-is is acceptable given the local pre-flight is clean and prod tables are likely small.
- Risk: of fixing — re-baselining applied migrations is riskier than shipping; recommendation is pre-flight + accept. Of not fixing — brief write-blocking / an aborted deploy that `migrate resolve` + data fix recovers.
- Tests required: none (deploy runbook step).

### ADV2-5 [P3] `users/[id]` PATCH staff-target guard lags the r121-E3 policy — a MANAGE_USERS sub_admin can rename an `admin`/`sub_admin` account
- Type: FACT (policy asymmetry, not a takeover)
- Evidence: r121-E3 extended reset-password to all staff targets (`src/app/api/admin/reset-password/route.ts:33-45`), but the sibling `src/app/api/users/[id]/route.ts:52-54` still blocks only `target.role === "super_admin"`. The PATCH schema (`:9-14`) has no password field (no credential write — takeover impossible), but `username`/`name` of an `admin`/`sub_admin` are writable by any MANAGE_USERS holder.
- Impact: a sub_admin with MANAGE_USERS can rename a legacy `admin`'s username → login-lockout confusion for that account (staff can't sign in with the old handle) and audit-trail muddying. Not privilege escalation (passwords/roles/restaurantId remain super_admin-gated at :33-38).
- Fix (minimal): mirror the E-3 target list in users/[id] PATCH (block super_admin/admin/sub_admin targets for non-super_admin, name/username-only edits included), or document the split policy.
- Risk: of fixing — low (support flows for staff go through super_admin, same as passwords). Of not fixing — inconsistent guard family; cheap griefing vector inside the staff trust boundary.
- Tests required: unit — sub_admin(MANAGE_USERS) PATCH admin target name → 403; PATCH owner target name → 200 (regression).

### ADV2-6 [P3] Legacy single-slug pending payments (`tempRestaurantSlug`) are invisible to `isSlugHeldByPendingPayment` — the 3 new guarded paths can still snipe them
- Type: FACT (narrow: legacy pending rows only)
- Evidence: `src/lib/validation.ts:200-207` — the reservation check queries only `metadata: { path: ['tempRestaurants'], array_contains: [{ slug }] }`. The approval path still honors the legacy single-slug metadata (`src/lib/subscription-decisions.ts:219-223`: `meta?.tempRestaurantSlug` fallback), and `subscriptions` POST now always writes the array form (`api/subscriptions/route.ts:105`), so the gap is limited to pending payments created before the multi-menu era still sitting in the prod DB.
- Impact: an owner/staff slug write on the three newly-guarded paths (restaurants/[id] PUT, owner/restaurants POST, settings `restaurant_slug`) can take a slug held by such a legacy pending payment → approval hits SLUG_TAKEN inside the tx → payer stuck pending (the exact r103-F4 dead-end r121-C3 set out to close, for the legacy subset).
- Fix (minimal): OR a second findFirst on `metadata: { path: ['tempRestaurantSlug'], equals: slug }` inside `isSlugHeldByPendingPayment` (one extra query on a rare path); or verify prod has zero legacy-shape pending rows and note it.
- Risk: of fixing — negligible. Of not fixing — a handful of possible stranded payers if legacy pendings exist.
- Tests required: unit — pending payment with legacy `tempRestaurantSlug` → reservation check returns true.
