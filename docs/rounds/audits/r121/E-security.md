## Findings

### E-1 [P1] Cross-tenant item move: PUT /api/items/[id] never validates the incoming `categoryId` — any owner can inject an item into another tenant's menu
- Type: FACT (code-proven)
- Evidence: `src/app/api/items/[id]/route.ts:92` — updateSchema accepts `categoryId: z.number().int().positive().optional()`; `:151-159` — the spread loop copies every body key except `modifierGroups` into `updateData` (categoryId included, verbatim); `:220-224` — `prisma.menuItem.update({ where: { id: itemId }, data: updateData })` writes it. The ownership ladder (`:130-149`) verifies the caller against the item's **current** `existing.category.restaurantId` only — the **destination** category is never fetched or checked. Contrast the sibling POST, which does it correctly: `src/app/api/items/route.ts:196-228` fetches the category and runs the owner/`UserRestaurant`/`MANAGE_RESTAURANTS` ladder on the target restaurant before creating.
- Impact: Owner A (any authenticated owner, or any `admin`/`sub_admin`+MANAGE_RESTAURANTS) sends `PUT /api/items/<own-item-id>` with `categoryId` = a category of restaurant B (ids are small sequential integers — trivially enumerable via the public menu API). The item — with A-controlled name/description/image/price — is now served on **B's public menu** (`/menu/<B-slug>`), orderable by B's customers, counted into B's plan cap and B's stats. That is a cross-tenant write primitive: menu defacement + order-stream/stat pollution for an arbitrary tenant, with zero privilege beyond owning any restaurant. After the move A loses edit rights to the row (ownership re-reads the new restaurantId), so it is a fire-and-forget injection, not persistence.
- Fix (minimal, root-cause): mirror the POST check — when `body.categoryId` is present, fetch the target category and require `targetCategory.restaurantId` ∈ {caller's primary} ∪ {UserRestaurant links} (owners) or MANAGE_RESTAURANTS (staff) before the update; reject with the standard 403 otherwise.
- Risk: of fixing — low (one conditional block; legitimate in-tenant category moves still pass). Of not fixing — any owner can deface any other tenant's live menu and pollute their orders/stats; direct tenant-isolation break on the product's core surface.
- Tests required: unit — owner A PUT own item with B's categoryId → 403, row unchanged; owner A PUT with own second category → 200; sub_admin w/o MANAGE_RESTAURANTS + foreign categoryId → 403. e2e — two seeded tenants, move attempt across.

### E-2 [P2] Web-panel payment approval lacks the self-approval guard the Telegram webhook has (r118-A2-P2 closed only one of the two surfaces)
- Type: FACT (code-proven)
- Evidence: `src/app/api/admin/subscriptions/route.ts:64-88` — POST verifies `MANAGE_SUBSCRIPTIONS` then calls `resolveSubscriptionPayment(id, status)` with **no check that the caller is not the payment's owner**. The webhook surface is guarded: `src/app/api/telegram/webhook/route.ts:89-101` blocks `isPaymentSelfApproval(paymentId, cq.from.id)` (impl at `src/lib/subscription-decisions.ts:70-80`), added r118-A2-P2 with the rationale that an approver "cannot resolve their own payment". Any authenticated user can mint their own pending payment: `src/app/api/subscriptions/upgrade/route.ts:138-157` (requireAuth-only; payment tied to `auth.userId`).
- Impact: a `sub_admin` holding MANAGE_SUBSCRIPTIONS (or a legacy `admin`, who passes every permission except MANAGE_USERS — `src/lib/auth.ts:71-76`) can: (1) POST /api/subscriptions/upgrade for a restaurant they own/manage → own pending payment; (2) POST /api/admin/subscriptions `{id, status:"verified"}` → approve **their own** payment → paid plan activated without money changing hands. Exactly the self-approval class the r118 guard was written to close, on the sibling surface.
- Fix (minimal): in `admin/subscriptions` POST, after the permission gate, load the payment's `userId` (or have `resolveSubscriptionPayment` accept an optional `actorUserId`) and return 403 when it equals `auth.userId` — the panel-side twin of `isPaymentSelfApproval`.
- Risk: of fixing — negligible (super_admin approving a payment they themselves filed is a pathological case anyway). Of not fixing — financial-integrity hole for every MANAGE_SUBSCRIPTIONS holder who also owns a restaurant.
- Tests required: unit — sub_admin(MANAGE_SUBSCRIPTIONS) approves own payment → 403 + payment stays pending; approves someone else's → 200. Keep webhook self-approval tests green.

### E-3 [P2] Password-reset target guard blocks only super_admin — a sub_admin with MANAGE_USERS can reset the legacy `admin` account's password and take over the platform
- Type: FACT (code chain; one runtime premise UNVERIFIED — see Impact)
- Evidence: `src/app/api/admin/reset-password/route.ts:37-39` — the only target guard is `if (target.role === "super_admin" && auth.role !== "super_admin")`. The code comment (round90-F1) shows intent to stop exactly this class ("sub_admin يحمل MANAGE_USERS كان يعيد كلمة مرور super_admin ويسحب جلساته = استيلاء كامل") but stops at super_admin. A role-`admin` target is resettable by any MANAGE_USERS holder. The legacy `admin` role is full-trust everywhere: `src/lib/auth.ts:71-76` grants it every permission except MANAGE_USERS, and `src/lib/stats-queries.ts:64` / `requireAdmin` treat it as staff-full-access. The seeded `admin` account exists by design: `src/app/api/seed/route.ts:35-37` (role: "admin"). The sibling routes show the intended pattern of also shielding privileged targets: `users/[id]/route.ts:52-54` and `admins/[id]/route.ts:29` both block super_admin targets for non-super_admins.
- Impact: sub_admin(MANAGE_USERS) → reset `admin` password → login as admin → all restaurants, all settings, all subscriptions, Telegram config (everything except MANAGE_USERS itself) → de-facto platform takeover. Sessions of the victim are revoked by the reset (`:46`), so the takeover is silent and immediate. UNVERIFIED premise: whether a role-`admin` account exists in the production DB at HEAD (DB not queried — read-only audit; the seed path proves the role is live by design and r118 comments reference legacy admin accounts with empty permissions arrays, e.g. `owner/restaurants/[id]/route.ts:39-41`).
- Fix (minimal): extend the target guard to `admin` (and arguably `sub_admin`) targets: `if ((target.role === "super_admin" || target.role === "admin") && auth.role !== "super_admin") return 403` — MANAGE_USERS stays a support tool for owner/USER passwords, which is its documented purpose.
- Risk: of fixing — low (support workflows resetting an admin's password can go through super_admin). Of not fixing — single-permission sub_admin compromise escalates to platform admin.
- Tests required: unit — sub_admin(MANAGE_USERS) reset on admin target → 403; on owner target → 200 (regression); super_admin on admin → 200.

### E-4 [P3] /admin and /owner page routes are server-gated only by cookie *presence* — any ≥32-char fake cookie renders the dashboard shells
- Type: FACT (code-proven)
- Evidence: `src/proxy.ts:218-226` — for PROTECTED_ROOTS (`/admin`, `/owner`) the edge gate is only `if (!session || session.length < 32)` → redirect to /login; otherwise `NextResponse.next()`. No server component in either tree validates the session: every page under `(protected)/admin` and `(protected)/owner` is `'use client'` (verified: layouts + all page.tsx greps; only `/login` uses server-side `requireAuth` — `login/page.tsx:48`). Full DB-backed auth happens later in each API route.
- Impact: an anonymous visitor setting `smart-menu-session=aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa` gets the full admin/owner dashboard shells — navigation, i18n strings, client bundle — before the client-side `useAccessGate`/`/api/auth/me` 401 kicks them out. No data exposure (all data APIs validate), but the r113 "66-route anonymous auth matrix" covered only /api/* — this is the page-route equivalent it couldn't see, and it weakens the "admin surface invisible to anonymous users" property (shell + nav reveals admin feature taxonomy).
- Fix (minimal): make the two group layouts server components that `requireAuth()` and redirect (the exact pattern `login/page.tsx` already uses), or move the cookie-presence check to a real session-shape check; keep the proxy check as-is for the redirect UX.
- Risk: of fixing — low-medium (layouts become async server components; nonce/CSP flow must be re-checked — layouts already run under `connection()` via the protected root layout). Of not fixing — cosmetic/defense-in-depth only.
- Tests required: e2e — GET /admin with fake 32-char cookie → redirect to /login (not 200 shell); GET /owner with valid owner session → 200.

### E-5 [P3] Username-enumeration oracles on register + subscriptions/validate nullify the login route's DUMMY_HASH timing equalization
- Type: FACT (inconsistency; severity judgment)
- Evidence: login invests heavily in hiding username existence: `src/app/api/auth/login/route.ts:88-94` burns the full PBKDF2 cost on a missing user (`DUMMY_HASH`, `void verifyHash(...)` — synchronous `pbkdf2Sync`, so the burn is real) and returns a byte-identical 401. But `src/app/api/auth/register/route.ts:53-57` returns a distinct 409 «اسم المستخدم موجود مسبقاً» for any existing username (5/min/IP), and the CSRF-exempt, **unauthenticated** `src/app/api/subscriptions/validate/route.ts:38-49` confirms username existence (10/min/IP). Both are cheaper and faster oracles than timing the login path.
- Impact: an attacker can enumerate valid usernames at 10-15/min/IP (more with rotation on non-Vercel) without ever touching the equalized login path. Usernames are then the lockout-backstop key (`acct:${username}`, `login/route.ts:105`) — a valid username list also enables targeted lockout DoS (20 failures/15min locks the name for everyone).
- Fix (minimal, judgment): this is a product tradeoff (signup UX needs the 409; the validate pre-flight is its designed purpose). If tightening: make validate require proof-of-intent (it already skips the caller's own name) or collapse register's 409 into the login-style generic error and let validation UX rely on the validate route only for *available* names. At minimum, document the accepted oracle next to the DUMMY_HASH comment so a future round doesn't assume login is enumeration-safe.
- Risk: of fixing — medium UX cost (signup friction); of not fixing — enumeration remains cheap, which the login code explicitly treats as a threat.
- Tests required: none if documentation-only; if behavior changes — register duplicate-username contract tests must be updated (several suites pin the 409).

### E-6 [P3] Login's synchronous 600k-iteration KDF + per-(ip:username) limiter = per-IP-unbounded CPU/DB amplification (the /api/health DoS class r118-B1 fixed)
- Type: SUGGESTION (design observation)
- Evidence: `src/lib/hash.ts:42-46` — `pbkdf2Sync(..., 600_000, ...)` ≈ 290ms of **blocking** CPU per call (documented at hash.ts:3-5). `src/app/api/auth/login/route.ts:70-71` — the primary limiter keys `${ip}:${username}` (10/min), so a single IP sending N distinct usernames gets N×10 attempts/min; each missing-user probe (`:92`) burns the full sync KDF plus one `user.findUnique` plus one `RateLimitEntry` write (DB-backed, `src/lib/rate-limit.ts:72+`). The account limiters deliberately skip the missing-user path (`:37-39`), so nothing per-IP caps the aggregate burn. Precedent: r118-B1 added an in-memory 30/min/IP throttle to `/api/health` precisely because it was "the cheapest unauth Neon-compute DoS vector" (ENGINEERING_STATE r118 entry).
- Impact: one client can mint ~290ms CPU + 2 DB ops per request at high request rates (username space is unbounded), pinning Node event-loop time on standalone/self-hosted deployments and inflating Neon compute on Vercel (mitigated there by per-invocation lambdas — blast radius is cost/spam, not full outage).
- Fix (minimal): one cheap in-memory per-IP pre-check on the login route (same 30/min/IP pattern as health) before the KDF burn; DB-backed per-IP aggregate limiter would also work but adds a Neon write to the hot path (the opposite of the health fix's rationale).
- Risk: of fixing — low (shared-IP offices/NATs: 30/min/IP of *login attempts* is far above any legit cadence; the existing ip:username bucket stays for friendly 429 copy). Of not fixing — cheap unauthenticated compute/DB amplification remains.
- Tests required: unit — 31st login attempt from one IP within a minute → 429 before KDF (mock clock); existing lockout tests unaffected (they pin account-level budgets, not IP totals).

## Surfaces attacked and found SOLID (r113/r118/r119 held; new angles tried)

1. **Session lifecycle** (`src/lib/session.ts`): fresh UUID per login (no fixation vector — no path accepts a client-supplied session id); SHA-256-at-rest token lookup; 24h sliding with 7d absolute cap (`:193-199`) and clamped renewal (`:216-219`); 5-session cap inside one transaction with new-row protection (`:36-59`); logout retries deletion (`:93-101`); **r119-B6 verified end-to-end**: `logout/route.ts:12-19` revokes Bearer via `destroySessionByToken` + cookie via `destroySession`, both retry-once; admin password change revokes all sessions but the current cookie (`admin/profile/route.ts:108-117`; minor UX-only gap: a Bearer-authenticated password change deletes the caller's own mobile session too — fail-closed, not a hole). Token-shape regex gates all paths.
2. **CSRF** (`src/lib/csrf.ts` + `proxy.ts:198-205`): Origin anchored to platform truth (request URL host + NEXT_PUBLIC_DOMAIN; forwarded headers explicitly distrusted); constant-time double-submit (`:123-129`); exemption surface audited route-by-route — `/api/telegram/webhook` (secret-gated), `/api/health` (GET-only + throttled), `/api/subscriptions/validate` (read-only, verified), `/api/cron/*` prefix (CRON_SECRET timing-safe bearer — `cron/cleanup/route.ts:10-17`); the mobile unauth paths (`/api/auth/login`, `/api/orders`) require the custom `x-client-type` header, which is CORS-preflight-blocked cross-site, so the exemption cannot be driven by a browser forgery; the Bearer skip (`csrf.ts:65-68`) is preflight-safe for the same reason.
3. **SQL injection**: every `$queryRaw`/`$executeRaw` in app code (14 sites: stats/advanced ×8, admin/stats ×2, reviews ×2, FOR UPDATE row locks ×5, sitemap, menu/[slug]) uses tagged-template parameterization — zero interpolation of client input; all `orderBy` clauses are hardcoded literals (28 grep hits, none dynamic); no zod `.passthrough()` anywhere (only bounded `z.record`/`z.json()` in audited routes).
4. **XSS**: all 4 `dangerouslySetInnerHTML` sites are static or escaped (`HIGH_CONTRAST_BOOT_SCRIPT` constant; menu JSON-LD `<`→`\u003c`); no user-controlled `href`/`src` sinks — item images pass `mediaUrlError` (scheme allowlist + cross-tenant blob rejection, `blob.ts:58-71`), receipt URLs are `https://`-only (`subscriptions/upgrade/route.ts:27`), whatsapp links are `https://wa.me/`-prefixed, `tel:`/`sms:` targets are non-executable schemes; CSP is nonce+strict-dynamic on dynamic pages, static on ISR pages, with COOP/CORP/HSTS/XFO/nosniff set in the proxy.
5. **Secrets**: `scripts/check-secrets.mjs` → 1067 files, 0 leaks, 50 documented dev-only exceptions; my supplementary scans (PEM private keys, `bot<id>:<token>` Telegram format, ≥64-hex, ≥80-base64, excluding generated/docs/tests) → clean; `NEXT_PUBLIC_*` = DOMAIN/WHATSAPP_NUMBER/APP_URL only; env validation enforces `AUTH_SECRET ≥ 32` / `JWT_SECRET ≥ 64` (`env.ts:22,29`); admin config values encrypted at rest (AES-GCM HKDF-derived key, `keys.ts`), masked on read, `isSecret` cannot be silently dropped (`admin/config/route.ts:80-97`); bot token trimmed at registration (r118) and never returned raw.
6. **Telegram webhook chain** (`telegram/webhook/route.ts`): fail-closed 403 when secret unset (`:204-213`), timing-safe secret compare before rate-limiting (`:215-223`), non-JSON probes acked without processing (`:227-230`), callback gate = allowlisted admin Telegram ids (`:53-68`), self-approval guard (`:89-101`), idempotent/conflict-aware decisions via `resolveSubscriptionPayment` (pending-conditional updates + `FOR UPDATE` serialization + server-side plan caps); `/start verify_` link tokens are HMAC-signed, 5-min exp, single-use via atomic rateLimitEntry create (shared namespace with the panel verify path), and generator-bound (`admin/telegram/verify/route.ts:74-76`); a forged update is unreachable without the webhook secret, and a replayed admin tap lands in the idempotent/conflict arms, not a re-grant.
7. **Login/lockout hardening** (`auth/login/route.ts`): 3-tier limits (10/min `ip:username`; 20/15min `acct:ip:username` failure-only; 20/15min username-only rotation-proof backstop), lockout SystemEvents, identical 401 bodies, sync KDF timing equalization (see E-5/E-6 for the residual oracles), transparent rehash on login, generic 500s.
