## D4 — 404 لمسارات API غير الموجودة يعيد HTML (من تقرير A · LOW-4)

**الظاهرة المقيسة** (A): `GET /api/nonexistent-r94-audit-xyz` → 404 لكن `content-type: text/html`، `x-matched-path: /404`، و49,130 بايت من HTML كاملة (صفحة not-found العامة المبنية بالعلامة التجارية).

**القرار: نتركها كما هي — لا تغيير. المبرر:**

1. **سلوك Next.js 16 البنيوي**: المسار غير المطابق تحت `/api/*` يسقط إلى `not-found.tsx` الجذرية (البنية العامة للتطبيق). هذه ليست عيباً محلياً في كودنا بل التصميم الافتراضي لإطار التوجيه — تغييره يتطلب إضافة catch-all route handler (`src/app/api/[...notfound]/route.ts`) **لا وجود لأي نمط مشابه له في المشروع** (كل مسارات API معرّفة حرفياً؛ لا يوجد أي catch-all).
2. **كلفة الحل أعلى من مظهره**: catch-all صحيح يحتاج تصدير مصفوفة HTTP methods كاملة (GET/POST/PUT/PATCH/DELETE/HEAD/OPTIONS) وإلا تحوّل أخطاء 404 الحالية إلى 405 فارغة لغير-GET — تراجع سلوكي أسوأ من HTML اللطيف الحالي؛ ويغيّر سلوكاً تقيسه حراس الإنتاج (team10 يفحص ترويسات 404 والفارق بين 404-API و404-الصفحات جزء من بصمات الجولات 79-87).
3. **حجم الأثر الفعلي**: حالات الالتفاف هذه ناتج أخطاء إملائية/تشخيصية من مطورين، لا عملاء حقيقيين — كل عملاء API الحقيقيين يضربون مسارات موثقة. الـHTML يعاد مع `no-store` وبلا كاش.
4. **السابقة**: أُجل البند في r93 بنفس التعليل، وأعيد قياسه فقط في r94 دون ترقية خطورته (LOW).

**متى نعيد فتحه؟** إذا أبلغ عميل API حقيقي عن parse-failure على مسار غير موجود، أو مع موجة تحسين API عامة (المكان الطبيعي: route handler للـcatch-all مع مصفوفة methods كاملة + اختبارات).

## MED-2 — صور المنيو الخارجية (Unsplash) «تتجاوز /_next/image»

**نتيجة إعادة التحقق الحية (W3، اليوم، على الإنتاج): الفرضية الأساسية في تقرير A غير دقيقة.** فحص Playwright مباشر على `https://menu.smart-link.ly/menu/al-waha-cafe` أثبت أن الـ16 صورة أصناف المعروضة **كلها تُقدَّم عبر `/_next/image?url=https%3A%2F%2Fimages.unsplash.com%2F...`** (نفس الأصل) — أي أن المحسِّن يعمل فعلاً (avif + كاش طويل + `sizes` صحيح من r88-A2)، وأن طلبات المتصفح لا تذهب إلى unsplash مباشرة. أرقام «20 صورة avif (Unsplash)» في تقرير A تصنيفٌ خاطئ من أداة القياس (البايتات وصلت من المحسِّن نفسه الذي يجلب من unsplash **خادمياً**).

**الحالة الفعلية للكود:**
- `remotePatterns` في next.config.ts يشمل `images.unsplash.com` + `plus.unsplash.com` ✓ (جاهز أصلاً).
- بطاقات الأصناف (MenuItemCard → OptimizedImage) تستخدم `next/image` فعلاً ✓ — لا يوجد «تحويل <img> لـImage» مطلوب.
- الموقعان اللذان يستخدمان `<img>` خاماً كلاهما **مقصود**:
  1. `GalleryCarousel.tsx:264` — معلَّق في الكود: الـlightbox يحتاج `object-contain` مع قيد ارتفاع، وهو تخطيط غير مدعوم بـ`fill` في next/image.
  2. `MenuToolbar.tsx:261` — مصغّرة 40px في نتائج البحث (زخرفية `aria-hidden` + lazy): الخام هنا **أكثر أماناً** — `next/image` يرمي استثناء على أي hostname غير مدرج في remotePatterns، وصورة الصنف قد تكون URL خارجياً تعبئه بيانات قديمة (الخام يتدهور بلطف بدل كسر نتائج البحث).

**البقايا الحقيقية (خارج نطاق الكود — قرار بيانات للمالك):** مصدر الصور نفسه جهة خارجية (unsplash CDN يجلب منها المحسِّن خادمياً) — توافر/خصوصية/سيادة بيانات. الحل الجذري: نقل صور الديمو إلى Vercel Blob (النمط الموجود أصلاً للصور المرفوعة) وتحديث صفوف DB — موجة بيانات مستقلة، لا إصلاح كود.

**الخلاصة: لا تغيير كود** — التكليف اشترط «إن كان إصلاحاً بسيطاً (المسارات جاهزة والمكون يستخدم Image أصلاً) نفّذه»، والتحقق أثبت أن هذا هو الوضع القائم أصلاً.

## fafaef في sitemap (من تقرير A · LOW-9) — توثيق فقط، لا إصلاح

**السبب مفهوم ومقصود ومُختبَر**:

- `updatedAt=2026-07-05` (~65 يوماً وقت التفتيش) → ينجو من بوابة النشاط 90 يوماً.
- هذا **حد موثَّق بعقد اختبار**: `tests/unit/r92-sitemap-filter.test.ts` (الحالة «حدود موثقة: عبث غني بالحروف المتحركة حديث التحديث ينجو») تثبّت أن هذا السلوك مقصود — «الأنماط الأقوى تخاطر بالمطاعم الحقيقية»، والحل الجذري «تنظيف DB». تحويل الاختبار اليوم ليناقض فلسفته الموثقة = كسر عقد مقصود.
- **إصلاح كود محصور ممكن نظرياً** (إضافة السلايغ الحرفي إلى JUNK_SLUG_PATTERNS) لكنه overfitting لصف قمامة واحد: أي قمامة جديدة بلا نمط ستنجو بنفس الطريقة، والسطر المضاف يخالف تعليق القائمة نفسه («KNOWN garbage shapes» عائلات، لا صفوف فردية).

**الترتيب الزمني الذاتي**: ما لم يُحدَّث الصف مجدداً، يسقط fafaef من الـsitemap تلقائياً حوالي 2026-10-03 (90 يوماً بعد آخر تحديث). الحل الجذري قرار بيانات للمالك (تعطيل/حذف الصف — نفس قرار MED-1 لمطاعم الديمو الثلاثة).
